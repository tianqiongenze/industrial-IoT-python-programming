# 05 运行手册

## 1. 环境准备
```bash
conda activate pp03          # Python 3.12 + SQLAlchemy 2.1.3（课程环境）
pip install -r requirements.txt
python check_env.py          # 可选：课程环境自检（仓库根）
```

## 2. 运行
```bash
python run.py                        # 完整流水线：建库→种子→缓冲导入→查询→溯源→聚合→交接→分层报告
python run.py --query avg-vib        # 只打印统计查询：avg-vib/top-alarms/hourly/window/all
python run.py --index-bench          # 强制重新实测索引前后耗时与 EXPLAIN（刷新 runtime/bench.json）
python run.py --buffer ../../buffer.db   # 指定 P4 缓冲库（默认取配置 buffer_db）
python run.py --config X --outdir Y --quiet
python -m pytest -q                  # 全量测试（57 项）
```

## 3. 配置说明（config/rules.yaml；15 个键均被代码读取，改配置不改代码）
| 键 | 含义 | 读取方 |
|---|---|---|
| db_url | SQLite 库 URL（相对路径自动锚定本项目 output/） | pipeline.ensure_db |
| buffer_db | P4 缓冲库路径；缺失自动用确定性替代源并在报告声明 | pipeline.ensure_db |
| seed | 随机种子（可复现） | core.seed_demo / import_buffer / index_bench |
| n_records | 种子记录数（D 层入库证据的量） | core.seed_demo |
| batch_size | 批量入库每批条数（每批一个事务；C 层批量事务判据） | core.seed_demo / import_buffer |
| warn / danger | vib 预警线/危险线(mm/s)，决定告警 level 1/2 | core.seed_demo |
| unit | 振动测点工程单位 | core.seed_demo |
| topk | 告警Top-K / 慢查询报告条数 | pipeline.query_rows / get_bench |
| index_bench_rows | 索引基准副本表行数（0 = 空基准，B 层 EXPLAIN 证据即不成立） | core.index_bench |
| index_bench_reps | 索引基准重复次数（取中位） | core.index_bench |
| buffer_stand_in_rows | buffer.db 缺失时替代源行数（0 = 无缓冲数据，闸门据此如实判定） | core.import_buffer |
| min_stat_queries | D 层及格线：至少几条统计查询返回真实行（工单口径 2） | pipeline._tier_gates |
| n_plus_one_loader | B 层 N+1 规避手段：joinedload / selectinload / lazy（lazy=不规避） | core.n_plus_one_demo |
| p3_handoff | A 层 P3 仪表盘闭环交接文件名（置空=关闭交接，A 层判不达标） | pipeline.handoff_path |

## 4. 输出物
| 文件 | 归属 | 内容 |
|---|---|---|
| output/warehouse.db | 交付证据 | 四表数据仓库（含 idx_dev_ts 联合索引） |
| output/report.txt | 交付证据 | D/C/B/A 分层过程报告（ER、溯源、数据字典、查询行、环比、四表聚合、P3 交接、EXPLAIN 计划、「分层达标」四行） |
| output/result.json | 交付证据 | 结构化结果 + `tiers`/`tier_criteria`/`evidence`（答辩取数） |
| output/p3_dashboard_handoff.csv | 交付证据 | A 层闭环交接文件：36 行×6 列（ts/device_id/line/temp/vib/status），P3 可直接读 |
| runtime/bench.json | 本地实测 | 索引基准前后中位毫秒、提速倍数、慢查询中位毫秒（基准参数变更即失效重测） |
| runtime/bench.db | 本地实测 | 索引基准同构副本表（index_bench 的写入目标，不污染业务库） |

`runtime/` 已在 .gitignore：墙钟毫秒属"本次机器实测"，进 output/ 会让逐字节复现闸门失效。

## 5. 可复现性口径
- 默认两次连续运行：`output/` 除 report.txt 首行"生成时间"外**逐字节一致**
  （sqlite 文件先删后建 + 固定 seed + `hash_of()` 代替内置 `hash()`，故与 PYTHONHASHSEED 无关）。
- 墙钟毫秒一律只写 `runtime/bench.json`，output/ 内任何产物（含报告、JSON、CSV）都不含时间值；
  B 层判定看确定性执行计划形态（SCAN → SEARCH USING INDEX），不看快慢。
- `--index-bench` 会刷新 runtime 缓存中的毫秒数——这是刻意的"重新实测"动作，非默认路径。
- 基准缓存键含 rows/reps/seed/topk：改基准参数会自动重测，不会拿旧毫秒冒充新配置。
- P4 buffer.db 缺失时自动切替代源，替代源同样确定性（seed 固定、行数由 buffer_stand_in_rows 决定），报告注明来源。

## 6. 常见问题
| 现象 | 原因 | 处置 |
|---|---|---|
| database is locked | P4 采集进程占用同一路径 sqlite | 先停采集或用 WAL；本项目库文件独立在 output/ |
| 'No such function: date_trunc' | SQLite 没有该函数 | 用 func.strftime（本项目即此口径） |
| 索引对比看不到加速 | 样本太小 | 已按 index_bench_rows 大样本实测；若仍无加速，报告如实呈现（且毫秒不进 output/） |
| 关系属性触发一堆 SQL | N+1 | joinedload/selectinload 预加载（报告含真实 SQL 计数取证） |
| 某档报"未达标" | 该级判据的实测数字不成立（如孤儿行>0、命中 0 行、交接列为空） | 看「分层达标」行点名的数字，按 docs/03 §6 补对应能力；不要改判定代码 |
| 溯源命中率不到 100% | 记录/告警挂到了别家设备的测点（典型是 `zip(devices*2, points)` 错位） | 用 `{(设备编码,指标): point_id}` 真实外键映射指派（见 docs/04 DEF-3） |
| 改了 index_bench_rows 但报告没变 | 只可能发生在参数没被 YAML 真正覆盖时 | `python run.py --index-bench` 重测；runtime/bench.json 的 params 会写明本次基准 |

## 7. 与 P3 仪表盘的闭环演示
```bash
python run.py --quiet                                        # P5 产出 output/p3_dashboard_handoff.csv
cd ../p33_kpi_cockpit && python run.py --source csv \
    --csv ../p55_warehouse_orm/output/p3_dashboard_handoff.csv   # P3 读 P5 仓库聚合结果出仪表盘
```
交接列只给采集仓库真实可得的 6 列；生产计数 `output/ok_qty/yield_pct` 由 P3 按其
provenance 规则标"合成·seed"，P5 不伪造。
