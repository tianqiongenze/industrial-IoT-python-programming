### 知识四要素详解（V1.2深度版·与授课PPT同源）

**B01 标准目录结构**
- 定义：目录即车间布局：src生产区/tests质检区/config图纸/data原料
- 使用场景：工程模板骨架——新项目复制即用不重搭
- 应用实例：src/cleaner.py + tests/test_cleaner.py 成对出现
- 扩展与误区：误区：全堆一个根目录——reviewer看目录就懂分层，混放=不及格
- 原理：标准目录结构把'谁都能看懂'变成物理事实：src放代码、tests放测试、data放数据、docs放文档——新成员clone即上手
- 判断依据：团队协作的第一块基石：目录即分工——你改src、他改tests互不踩脚
- 逐行解释：project/ ├src/ ├tests/ ├data/ ├docs/ └requirements.txt ——README三行说明每个目录放什么；import路径因src统一而不乱
- 进阶优化：进阶src布局(src/project_name/)防命名冲突；pyproject.toml现代打包配置替代setup.py

**B02 venv/conda沙箱**
- 定义：虚拟环境=每台机器各配工具箱：A要库1.0、B要2.0互不打架
- 使用场景：多人协作/多项目共存的版本冲突解法
- 应用实例：conda create -n pp03 && conda activate pp03
- 扩展与误区：误区：不激活就pip install——装进base等于白装，命令行看前缀
- 原理：venv/conda沙箱=项目级独立Python：每个项目一套依赖，A项目numpy 1.x、B项目2.x互不打架——不再污染全局
- 判断依据：任何项目开工第一件事建沙箱：conda create -n pp03 python=3.12；activate后再pip install
- 逐行解释：conda create -n pp03 python=3.12 建环境；conda activate pp03 进入；pip install -r requirements.txt 装依赖——三步一个干净世界
- 进阶优化：conda list导出environment.yml可复现；pip freeze>requirements.txt锁版本；退出deactivate——沙箱进出有门

**B03 Git五步工作流**
- 定义：Git五步=写日记五连：clone取本子→add记→commit存→branch分册→merge合册
- 使用场景：模板即资产：Git记录就是可追溯的开发档案
- 应用实例：git add . && git commit -m 'feat: 工程模板'
- 扩展与误区：误区：一周一commit大杂烩——小步提交才能回滚到任意中间态
- 原理：Git五步工作流=status→add→commit→push→pull：本地暂存区是'草稿箱'，commit是'定稿'，push才上远端——三层保险
- 判断依据：每天下班前必须push（本地盘坏了代码还在云端）；开工先pull同步他人进度防冲突
- 逐行解释：git status 看改动；git add . 进草稿；git commit -m 'feat: P1.2完成' 定稿；git push 上云；git pull 同步——五步成肌肉记忆
- 进阶优化：git diff看具体改动再add；git log --oneline翻历史；冲突时<<<标记三段取舍后重新add-commit

**B04 commit前缀**
- 定义：前缀=提交的分类标签：feat新功能/fix修bug/docs文档/test测试
- 使用场景：教师按前缀审贡献——message质量即工程素养
- 应用实例：feat: 完成P1.2目录规范 + .gitignore
- 扩展与误区：误区：'改了一些东西'式message=日记写'今天有事'——无法回溯
- 原理：commit前缀给提交贴类型标签：feat新功能/fix修bug/docs文档/refactor重构/test测试——历史即变更日志，可读可检索
- 判断依据：团队规约：无前缀commit不予合并——git log --grep=feat秒筛功能演进史
- 逐行解释：git commit -m 'fix: 修复3号PLC断线重连死循环' 前缀+模块+动作——三要素写全，半年后还能看懂
- 进阶优化：Conventional Commits标准（feat/fix/chore...）；commit message体写why不写what（diff已说明what）

**B05 pylint与black**
- 定义：pylint=机器质检员打分；black=自动整形师——先过机器再过人
- 使用场景：代码审查的机器闸门——pylint≥8.5是工单硬指标
- 应用实例：black src/ 秒级格式化；pylint src/ 出分
- 扩展与误区：误区：风格争议人肉吵——交给black零讨论成本，pylint只看逻辑分
- 原理：pylint静态扫描打分（10分制）抓命名/复杂度/坏味道，black自动格式化（不可配置、无争议）——机器管风格，人管逻辑
- 判断依据：提交前跑pylint src/ ≥8.0分门槛；black src/一键统一格式——代码评审不再吵架缩进
- 逐行解释：pylint src/w6.py 输出评分+问题清单（C0103命名不规范之类）；black src/ 全仓库重排——工具替你守门
- 进阶优化：pyproject.toml里[tool.black]统一团队配置；pylint --disable=C0103关掉团队不采纳的规则——规则要裁剪不要全收

**B06 pytest自动发现**
- 定义：pytest=自动点名的考官：test_开头文件与函数自动收集执行
- 使用场景：TDD入门——先写test_clean再写clean，测试先行
- 应用实例：def test_clean(): assert clean('脏') == '净'
- 扩展与误区：误区：测试文件名不带test_前缀——pytest根本不收，跑了等于没跑
- 原理：pytest自动发现：文件名test_*.py、函数名test_*即被收集，无需注册——断言用裸assert，失败自动展示上下文
- 判断依据：回归防线：每修一个bug写一个test_函数锁住——下次改坏立刻红
- 逐行解释：def test_parse(): assert parse('PUMP-03:78.5')==78.5 —— assert即测试；pytest tests/ 一键跑全部，绿点过红叉挂
- 进阶优化：pytest -k plc按关键词筛跑；fixture共享测试数据；参数化@pytest.mark.parametrize一次测多组边界
