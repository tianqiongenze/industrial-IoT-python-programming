# 07 架构决策记录 ADR-001（v2 更正）：数据访问层采用 SQLAlchemy 2.x ORM

- 状态：已接受（取代 v1"自研极简 ORM"决策）；v3 追加 ADR-002/003（见下）
- 日期：2026-10-27（v1：2026-10-14；ADR-002/003：2026-10-28）
- 决策者：项目组（师傅/组长评审）

## 背景
工单 P5 明确要求 ORM 模型用 **SQLAlchemy 声明式**（DeclarativeBase/ForeignKey/
relationship/Session/bulk）。v1.0 为"讲透原理"自研了 30 行极简内存 ORM，并以
ADR 合理化——这偏离了工单决策矩阵的选型约束（裸SQL/Core/ORM 三选一，课程指定 ORM），
也与 requirements.txt"仅标准库"自洽但违背需求权威。**本 ADR 正式更正该决策**，
原理教学目标改由 N+1 取证、EXPLAIN 实测等真实证据链完成。

## 决策矩阵（数据访问方式，工单 P5 原表回填）
| 方式 | 开发效率 | 性能可控性 | 团队协作 | 决策 |
|---|---|---|---|---|
| 裸 SQL | 低（手写映射） | 高 | 易分歧（方言） | 聚合报表兜底通道（session.execute(text(...))） |
| SQLAlchemy Core | 中 | 高 | 中 | 不选：教学口径是声明式 ORM |
| SQLAlchemy ORM | 高（类即表） | 中（可回退裸SQL） | 高（类型进IDE） | **采用** |

## 决策
**采用 SQLAlchemy 2.x 声明式 ORM**（pp03 环境 SQLAlchemy==2.1.3，SQLite 后端）。

## 实现要点
- 四表 DeclarativeBase；`Index('idx_dev_ts', point_id, ts)` 入 `__table_args__`；
- PRAGMA foreign_keys=ON（引擎 connect 事件）使外键约束真正生效；
- 批量入库 bulk_save_objects 分批事务并统计提交次数；复杂聚合保留裸 SQL 双形态互证；
- N+1 用事件监听真实计数取证（joinedload/selectinload 预加载，lazy 作对照）；
- 记录/告警的设备归属一律由外键与 `{(设备编码,指标): point_id}` 映射得出，不按列表顺序推断。

## 后果（ADR-001）
- 正面：与工单/教材（项目4）一致；生产可平移 PostgreSQL（只换 URL）；证据真实。
- 代价：新增第三方依赖；"手写ORM懂原理"的教学侧收益改由 EXPLAIN/SQL计数证据补位。
- 缓解：docs/03 保留双形态查询对照；README 标注课程环境与版本锁定。

# ADR-002：工单四档（D/C/B/A）用逐条实测闸门判定，禁止硬编码"达标"

- 状态：已接受（2026-10-28）
- 背景：工单 P5 给出四档验收表，四行**逐字原文**为「4表设计合理；ORM入库成功；2条统计查询可用」
  「数据字典完整；批量事务；溯源查询正确」「索引优化有EXPLAIN证据；N+1问题已规避」
  「优秀+复杂查询(多表JOIN聚合)+导入P3仪表盘形成闭环演示」，由 `pipeline.WO_ROW` 单点持有。
  项目此前只在报告里排了 D/C/B/A 段，`output/result.json` 里没有 `tiers`，四档实际不可判——
  与同批次 p41/p66 已有的分层闸门口径不一致，属交付缺口。

## 决策矩阵（四档如何落地）
| 方案 | 优点 | 风险 | 决策 |
|---|---|---|---|
| 报告里印四行固定"达标"文案 | 省事、永远好看 | 橡皮图章，学生无从知道差在哪；教师无法复核 | **否决** |
| 只给一个总分/最高档 | 简洁 | 丢失"差哪一条"的可操作性；四档语义被压扁 | 否决 |
| 每档拆判据布尔 + 真实测量数字 + 逐级累加，输出 `tiers`/`tier_criteria` 与带数字的四行 | 每条判据可独立复核、可被配置证伪；未达标即指出实测缺口 | 必须为判据补真实能力（溯源、手算互证、交接文件等） | **采用** |

## 后果
- 正面：四档全部由本次运行测量；`tests/test_tier_gates.py` 证明每一档都能"只改 rules.yaml
  不改代码"被判未达标（D：n_records/buffer_stand_in_rows=0、min_stat_queries=4；
  C：batch_size=1000；B：n_plus_one_loader=lazy、index_bench_rows=0；A：p3_handoff 置空），
  判定不是装饰；闸门反过来抓出 DEF-3（seed 测点错位）这一真实数据缺陷。
- 代价：新增 dictionary_coverage / traceability_check / device_hourly_summary + 手算互证 /
  export+validate_p3_handoff 等实现与 18 项测试；跨项目契约（P3 列名与时间格式）需长期同步。
- 缓解：契约集中为 `core.P3_CONTRACT_COLUMNS`/`P3_TS_FORMATS`，并有真调 P3 代码的读通测试；
  "未达标怎么补"写在 docs/03 §6，学生按行内数字自查。

# ADR-003：墙钟实测毫秒移出 output/，落 runtime/；B 层判据改用确定性事实

- 状态：已接受（2026-10-28）
- 背景：`../verify_local.py` 的 repeat 闸门用两个 `PYTHONHASHSEED` 各跑一次 run.py 并逐字节
  比对 output/。索引前后耗时、提速倍数、慢查询中位耗时是墙钟值，放 output/ 里要么每次变（
  复现必挂），要么被 mask（等于把不可复现数值伪装成证据）。同批次 p21/p66 已确立 runtime/ 口径。

## 决策
1. 实测毫秒与其载体（基准副本库）写 `runtime/bench.json`、`runtime/bench.db`，`runtime/` 进 .gitignore；
2. output/ 只保留确定性视图 `_bench_view`：基准行数、重复次数、区间命中行数、EXPLAIN 前/后计划行、
   `scan_before`/`index_search_after` 布尔、基准参数与"毫秒在 runtime/bench.json"的指路字段；
3. B 层 EXPLAIN 判据只看计划形态（SCAN → SEARCH … USING INDEX）与命中行数>0，不看快慢；
4. 基准缓存键 = rows/reps/seed/topk：参数一改立即重测，避免旧证据冒充新配置；
5. N+1 取证用 `before_cursor_execute` 计数器（确定性 SELECT 条数），与墙钟无关，可直接进 output/。

## 后果
- 正面：output/ 在任意 `PYTHONHASHSEED` 下逐字节可复现；B 层证据变成可断言的确定性事实；
  基准写入不再污染业务库 warehouse.db。
- 代价：报告里看不到"提速 14.5x"这类数字，需自行查看 runtime/bench.json；多一个 runtime/ 目录。
- 缓解：报告「B层·索引优化」段注明毫秒去处；`--index-bench` 一键重测；
  `test_tier_gates.py::test_output_contains_no_wallclock_values` 用正则守住"output 无 ms"红线。
