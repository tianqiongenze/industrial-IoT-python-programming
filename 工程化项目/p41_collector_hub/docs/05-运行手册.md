# 05 运行手册

## 1. 环境准备
```bash
conda create -n pp03 python=3.12 -y
conda activate pp03
pip install -r requirements.txt      # 或 requirements.lock
```

## 2. 运行
```bash
python run.py                     # 默认配置（只读 config/rules.yaml，零第三方依赖）
python run.py --config config/rules.yaml
python run.py --outdir output/
python run.py --quiet             # 只落盘，不打印「结论与建议」
p41_collector_hub                 # 安装为包后的 console script，与 run.py 同一个 cli.main
```
入口参数由 `src/collector_hub/cli.py::build_parser()` 定义，只有 `--config / --outdir / --quiet` 三个；
`run.py` 是把它接进来的薄壳（`from collector_hub.cli import main`）。

## 3. 配置说明（config/rules.yaml）
下表与 `config/rules.yaml` 逐字对齐（键名与取值均以本目录该文件为准）。

| 键 | 含义 | 默认 |
|---|---|---|
| warn | 预警线（本项目仅由 config 层承载，流水线不据此判达标） | 80.0 |
| danger | 危险线/停机线（同上） | 95.0 |
| batch_size | 每轮切批条数 | 3 |
| poll_rounds | 每个源的轮询轮数 | 4 |
| backoff_base | 指数退避基数（秒）：第 n 次重连等待 base×2ⁿ | 0.01 |
| retry_limit | 单条读数最多重连几次（0＝不重连，即对照组口径） | 3 |
| rate_target | 采集率达标线（%，C 层闸门用） | 95.0 |
| rate_pass_line | 工单及格(D)「采集率>95%」的验收线（%），改它即改验收口径 | 95.0 |
| rate_strict_target | 工单优秀(B)「采集率≥99.5%」的验收线（%） | 99.5 |
| latency_target_ms | 工单优秀(B)「延迟<100ms」的验收线（毫秒/条） | 100.0 |
| docs_min | 工单及格(D)「系统文档」要求的 docs/ 有效过程文档篇数（每篇 >200B） | 8 |
| unit | 单位口径 | c |
| seed | 随机种子（**当前流水线未用随机数**：读数由 crc32 确定性生成，此键仅保留配置兼容） | 7 |
| topk | 检索/排序取前 k（本项目未使用） | 3 |

数据源清单（`sources`，3 项；计划读数 = 3 源 × poll_rounds 4 × batch_size 3 = **36 条**）：

| id | host | port | scale（还原除数） | latency_ms（模拟单跳耗时） |
|---|---|---|---|---|
| PLC1 | 127.0.0.1 | 5020 | 10 | 12.0 |
| PLC2 | 127.0.0.1 | 5021 | 1 | 8.0 |
| PLC3 | 127.0.0.1 | 5022 | 100 | 20.0 |

链路故障注入（`faults`，共 3 处＝PLC2 两条 + PLC3 一条；`slots` 为该源第几条读数、1 基）：

| id | slots | fail_attempts（恢复前连续失败的尝试数） | 后果 |
|---|---|---|---|
| PLC2 | [4, 7] | 2 | 首读+1 次重连失败，第 3 次成功 → 重连可挽回 |
| PLC3 | [3] | 4 | 4 次尝试全失败 > retry_limit 3 → 该条计丢弃（烧掉 70ms 退避） |

> **顺序约束**：`faults` 必须写在 `sources` **之后**。`Settings.from_dict()` 取 YAML 中
> **第一个 list 型键**作为 `items`（即流水线的数据源清单）；若 `faults` 先出现，`items`
> 会变成故障表、流水线拿不到数据源。该约束由
> `tests/test_config.py::test_shipped_rules_declare_three_sources_and_faults` 用
> `cfg.items == cfg.raw["sources"]` 钉住。

## 4. 输出物
| 文件 | 内容 |
|---|---|
| output/report.txt | 完整过程报告（过程性证据），固定八节：输入口径 / 分源统计 / 链路可靠性对照（B层·断线重连实测）/ APM 面板（A层）/ 对账 / 工单验收四档对照（及格/良好/优秀/超优）/ 分层达标 / 结论与建议 |
| output/result.json | 结构化结果（供下游/答辩取数）：`sources` `per_source` `reconcile` `n_total` `planned` `injected_faults` `apm` `apm_no_retry` `collection_rate` `rate_no_retry` `rate_target` `identities` `tiers` `workorder_tiers` `workorder_evidence` `config_echo` |

出厂配置下两条链路的实测差（`python run.py` 可复核，报告首行时间戳除外逐字节一致）：

| 口径 | 计划 | 成功 | 丢弃 | 重试 | 传输调用 | 采集率 | 平均延迟 |
|---|---|---|---|---|---|---|---|
| 不重连（retry_limit=0） | 36 | 33 | 3 | 0 | 36 | 91.67% | 13.33ms |
| 指数退避重连（retry_limit=3） | 36 | 35 | 1 | 7 | 43 | 97.22% | 19.50ms |

计数自洽：成功+丢弃=计划 → 35+1=36；调用=成功+丢弃+重试 → 43=35+1+7。
累计退避等待 130.00ms，单条最长等待 70.00ms。

工单优秀(B) 不用上表这两条链路，而是新增**第三条**：把重连上限抬到吞得下最严重故障
（`faults` 里最大的 `fail_attempts` = 4，取 `max(retry_limit, 4, 1)` = 4）的「零丢弃链路」，
实测 计划 36 → 成功 36、丢弃 **0**、采集率 **100.00%**、平均延迟 **22.28ms/条**（比默认链路
19.50ms 慢，报告刻意取这条最保守的数）。该链路证据写在 `result.json` 的
`workorder_evidence.zero_link`（`retry_limit` `rate` `drop` `avg_ms`），
四条判定线 `rate_pass_line` / `rate_strict_target` / `latency_target_ms` / `docs_min` 同文件回显，
`workorder_tiers` 给出工单四档逐档 True/False。

> 只改配置就能翻档（无需动一行代码，均有对应用例钉住）：`rate_pass_line: 99.9` → 工单及格(D)
> 当场不达标；`latency_target_ms: 20.0` 或 `rate_strict_target: 100.5` → 工单优秀(B) 不达标；
> `docs_min: 99` → 及格(D) 的文档条款不达标；`retry_limit: 0` → 课堂 C/B 与工单 C/D 翻转，
> 而工单 B/A 因走零丢弃链路、只判计数自洽而不受影响（两套阶梯各判各的）。

## 5. 常见问题
| 现象 | 原因 | 处置 |
|---|---|---|
| `ModuleNotFoundError` | 未安装依赖 | `pip install -r requirements.txt` |
| `command not found: p41_collector_hub` | 未把本项目安装为包 | 直接 `python run.py`，或 `pip install -e .` 后再调用入口脚本 |
| 报告里没有「链路可靠性对照」 | 用了旧版代码/旧报告 | 重跑 `python run.py`；该节名与 `pipeline.run()` 的 sections 一一对应 |
| 配置不生效 | 未传 --config | 使用默认 `config/rules.yaml` |
| 中文乱码 | 控制台编码非 utf-8 | `set PYTHONIOENCODING=utf-8` |
