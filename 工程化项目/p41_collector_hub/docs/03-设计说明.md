# 03 设计说明

> 项目：多源数据采集中枢

## 2. 核心算法/规则
设计核心是**用确定性模拟把不可靠链路变成可对账的证据**，六条规则串起整条流水线：

1. **确定性模拟**：读数基线取 `250 + crc32(源ID) % 1000 % 7`，同一源恒定不变；内置 `hash()`
   受 PYTHONHASHSEED 随机化、跨进程会漂移，因此不作证据。链路故障由 `config/rules.yaml` 的
   `faults` 表按「该源第几条读数（1 基）+ 恢复前连续失败的尝试次数」定点注入，不用随机数。
   于是 36 条计划读数在任意机器跑两遍逐字节一致（`test_run_is_reproducible`）。
2. **可注入 transport 协议**：`transport(src, slot, attempt)`——`slot` 为该源本次会话内的读数
   序号（0 基），`attempt` 为第几次尝试（0 基＝首读），链路中断时抛 `LinkDown`。真实 pymodbus
   只要实现同一签名即可平替，`core` 层一行不改（对应 docs/01 F-01）。
3. **重试与退避引擎**：`read_retry()` 捕获 `LinkDown`，按 `sleep_with(base, attempt) = base × 2^attempt`
   累计退避后重连，最多重连 `retry_limit` 次；`retry_limit=0` 即「不重连」对照组。重试用尽仍失败时，
   异常带着**已烧掉的** `attempts` 与 `backoff_seconds` 上抛，`collect()` 把该条计入 `drop` 但保留其
   等待耗时——丢弃条目不许把成本一起丢掉（超上限 1 条即贡献 70ms 退避）。
4. **两条链路 A/B 对照**：`pipeline.run()` 用同一份故障配置跑两遍——`session(0)` 不重连对照组、
   `session(retry_limit)` 指数退避正式组，两者的计数差就是断线重连的实测收益：本轮
   **91.67% → 97.22%**（丢 3 条 → 丢 1 条，挽回 2 条，重连 7 次），报告
   「链路可靠性对照（B层·断线重连实测）」一节直接引用这两份 stats，不做人工标注。
   工单优秀(B) 要的是「采集率≥99.5% 且延迟<100ms」，上面两条都兑现不了（97.22% 仍丢 1 条），
   所以同一次 `run()` 里再跑**第三条**：`retry_limit = max(配置值, 最严重故障的 fail_attempts, 1)`
   = 4，即重连上限刚好吞得下最狠的那次故障 → 丢 0 条、采集率 100.00%、平均延迟 22.28ms/条。
   报告刻意用这条（而非更快的默认链路）作 B 档证据，因为它是同一份故障下最保守的一条。
5. **计数口径恒等式**：`planned` 含最终丢弃的条目，`calls` 计每一次传输调用（含首读），
   `retry = calls - planned`。由此得到 `check()` 强校验的两条自洽式：`成功+丢弃=计划`（35+1=36）
   与 `调用=成功+丢弃+重试`（43=35+1+7）；`merge()` 汇总分源时 `max_wait_ms` 取最大值、其余求和。
6. **可证伪的分层闸门**：`tiers` 的 D/C/B/A 四个布尔值全部由运行期计数推出——
   D＝对账恒等式＋计数自洽＋计划数吻合；C＝源数 ≥3 且采集率 ≥ `rate_target`；
   B＝注入数 >0 且重连次数 >0 且挽回条数 >0；A＝全局计数里
   planned/ok/drop/retry/calls/latency_ms/rate 七项齐备（面板实际输出十字段，另含
   backoff_ms/max_wait_ms/avg_ms，由 `test_a_layer_apm_panel_is_self_consistent` 逐项断言）。
   任一把配置改到不达标，
   闸门当场判 False：`test_config_only_change_can_fail_the_gate` 把 `retry_limit` 改成 0，
   C/B 立刻不达标而 D 仍成立；`test_no_fault_injection_reaches_full_collection` 撤掉全部故障，
   采集率 100% 而 B 层证据反而不成立。

## 3. 异常处理策略
| 异常 | 触发场景 | 处理 | 对应测试（真实节点名） |
|---|---|---|---|
| `LinkDown`（core 自定义） | transport 链路中断/读超时 | `read_retry()` 捕获后指数退避重连；用尽 `retry_limit` 则带 `attempts`/`backoff_seconds` 重抛，`collect()` 计入 `drop` 但保留等待耗时 | `tests/test_core.py::test_read_retry_gives_up_when_retries_exhausted`、`::test_collect_drops_only_beyond_retry_limit` |
| FileNotFoundError | 配置文件缺失 | 抛出并提示路径 | `tests/test_config.py::test_missing_config_raises` |
| ValueError | `restore()` 的 scale ≤ 0 | 立即失败，不输出错值 | `tests/test_core.py::test_restore_rejects_non_positive_scale[0]`、`[-1]` |
| ValueError | `rate()` 的 planned ≤ 0 | 立即失败，不返回 0% 假象 | `tests/test_core.py::test_rate_rejects_non_positive_planned[1-0]`、`[1--3]` |
| ValueError | `sources` 为空 | pipeline 启动即抛「config/rules.yaml 的 sources 为空」 | 无独立用例；由 `test_config.py::test_shipped_rules_declare_three_sources_and_faults` 保证出厂配置非空 |
| 除零保护 | 某源读数全部丢弃（`flat` 为空） | 均值取 0.0，不做 `sum/len` 除法 | `tests/test_tier_gates.py::test_config_only_change_can_fail_the_gate` |
| 自洽校验不过 | 计数被改脏（如 `calls=99`） | `check()` 判 False 并逐条指出哪条恒等式破了 | `tests/test_core.py::test_check_flags_inconsistent_counters` |

## 4. 命名与代码规范
- PEP 8；`snake_case`（函数/变量）、`PascalCase`（类）、`UPPER_CASE`（常量）
- docstring 三件套：做什么 / 参数 / 返回
- 单元函数 ≤40 行，超过则拆分；唯一例外是编排函数 `pipeline.run()`（线性装配＋报告分节，
  拆开反而打断证据链），其调用的每个算法步骤都在 `core` 里保持 ≤40 行
