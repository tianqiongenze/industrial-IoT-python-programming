# 03 设计说明

> 项目：产线数据仓库与 ORM（SQLAlchemy 2.x + SQLite）

## 1. 模块清单与接口
见 docs/02 表。核心设计点：

- **四表 ER**（工单 P5.1）：
  `devices(id, code, name, area)` ←1:N— `points(id, device_id, metric, unit)`
  ←1:N— `records(id, point_id, ts, value)`；`alarms(id, device_id, ts, level, message, resolved)` 挂设备。
- **联合索引**：`Record.__table_args__ = (Index("idx_dev_ts", "point_id", "ts"),)`
  ——覆盖"按测点查时段"最高频查询；最左前缀原则：仅按 ts 过滤不走该索引（慢查询报告里的教学反例）。
- **批量入库**：`bulk_save_objects` 每批 batch_size=100 条一个事务提交，并**统计真实提交次数**
  （seed_demo 5 次 + import_buffer 10 次 = 15 次，写入 result.json `evidence`），
  种子数据同样走 bulk（工单工程化要求3：禁循环单条 add）。
- **记录归属不靠列表顺序猜**：seed_demo 用 `{(设备编码, 指标): point_id}` 映射（由 relationship
  回读真实外键）给记录指派测点。早期写法 `zip(devices * 2, points)` 里 `devices * 2` 是序列重复
  `[D1,D2,D3,D1,D2,D3]` 而非逐设备重复 `[D1,D1,D2,D2,…]`，映射错位会让记录挂到别家设备的测点上，
  进而使溯源命中率与设备均值失真——这是分层闸门上线时由 C 层判据抓出的真实缺陷（DEF-3，见 §6）。
- **溯源查询**（core.py:366 `traceability_check`）：`alarms ⋈ devices ⋈ points ⋈ records`
  四表 JOIN，按 `Record.ts == AlarmEvent.ts` 且同设备反查告警那一瞬间的原始读数；
  同时用三条 LEFT JOIN + `id IS NULL` 清点 `records.point_id / points.device_id / alarms.device_id`
  的外键孤儿行。判定口径：命中告警数 == 告警总数 且 孤儿行 == 0。
- **数据字典完整性**（core.py:338 `dictionary_coverage`）：以 `FIELD_MEANINGS`（core.py:33）逐列
  登记含义，并用 inspector 列出四表全部列，产出「已登记列数 / 总列数 / 未登记清单」。
  SQLite 不持久化 `Column(comment=)`，故 comment 计数（8 列）只作补充证据不作判定依据。
- **复杂查询**（core.py:570 `device_hourly_summary`）：设备×小时四表聚合——
  records↔points↔devices 内连接 + alarms 按 (device_id, 小时) 外连接，
  聚合 `count(distinct(Record.id))`、`avg(case(metric…))` 分列温度/振动、
  `count(distinct(AlarmEvent.id))`、`max(level)`；并由 core.py:600 `device_hourly_manual`
  用 Python 逐行手算、core.py:630 `summary_matches_sql`（容差 0.005）逐行互证。
- **N+1 取证**（core.py:413 `n_plus_one_demo`）：`event.listens_for(engine, "before_cursor_execute")`
  计数器（core.py:425）分别跑 lazy / joinedload / selectinload 三种加载策略，记录各自发出的
  SELECT 条数。这是**确定性计数**，与墙钟无关，所以可以直接进 output/ 并作为 B 层判据。
- **P3 闭环交接**（core.py:654/680）：`export_p3_handoff` 把复杂聚合结果按 P3
  `p33_kpi_cockpit/src/kpi_cockpit/data_source.py` 的 `CANON` 列子集写成 6 列 CSV；
  `validate_p3_handoff` 再用 P3 的读法回验（列齐、时间按其 `_DT_FORMATS` 可解析、设备在册）。
  生产计数 `output/ok_qty/yield_pct` 不在采集仓库里，**由 P3 按其 provenance 规则标"合成·seed"，
  P5 不伪造**。P3 读通性由 `test_queries.py::test_p3_handoff_readable_by_p3_cockpit` 真调 P3 代码验证。
- **可复现策略**：sqlite 文件每次运行先删后建（页分配从零开始）+ 固定 seed + `hash_of()`
  代替内置 `hash()` ⇒ 任意 `PYTHONHASHSEED` 下两次运行 output/ 除报告"生成时间"行外逐字节一致；
  计时类实测（索引基准/慢查询中位毫秒）固化在 **runtime/bench.json**，后续运行读缓存，
  `--index-bench` 强制重测；**缓存键含基准参数**（rows/reps/seed/topk），参数一改立即失效重测，
  防止旧证据冒充新配置。
- **墙钟红线**：`before_ms / after_ms / speedup_x / note / ms` 一律不进 output/
  （`pipeline.WALLCLOCK_KEYS` + `_bench_view` 剥离），只在 `runtime/`；
  B 层 EXPLAIN 判据改用**计划形态**（SCAN → SEARCH USING INDEX）这类确定性事实。
- **索引基准**：为避免污染业务表，在独立 `runtime/bench.db` 的同构表 bench_records 上做大样本
  （index_bench_rows，默认 20000）实测：删表建表→取 EXPLAIN 前计划→计时→`engine.begin()`
  提交 `CREATE INDEX`（DDL 必须提交，否则连接池回滚后索引消失，"证据"是假的）→再取计划。
  若无加速会如实报告（本函数原样报告，不做任何粉饰）。

## 2. 核心算法/规则
| 查询 | 实现 | 说明 |
|---|---|---|
| T4a 各设备平均vib | select+join×2+where(metric='vib')+group_by+func.avg | 三表 JOIN |
| T4b 告警Top3 | alarms join devices group by count desc limit topk | 溯源 |
| T4c 按小时聚合 | func.strftime('%Y-%m-%d %H:00', ts) | SQLite 无 date_trunc |
| A层 环比 | LAG(cnt) OVER (ORDER BY hour)：ORM 用 func.lag().over()，裸 SQL 用 text()；两形态结果断言逐行相等 | |
| C层 溯源 | alarms→devices→points→records 四表 JOIN（ON 设备+同刻 ts）+ 三处孤儿行 LEFT JOIN 清点 | 命中率与孤儿数是实测值 |
| A层 复杂聚合 | 四表 LEFT JOIN + count(distinct)/avg(case)/max + 手算互证 | 设备×小时 36 桶 |
| N+1 取证 | event监听 before_cursor_execute 计 SELECT 条数 | 懒加载 4 条 vs joinedload 1 条 vs selectinload 2 条（3设备） |
| 分层判定 | 每级各判据取本次测量布尔值，`tiers` 逐级累加（C 含 D、B 含 C、A 含 B） | 见 §6 |

## 6. 分层达标闸门（tiers）与"未达标怎么补"
判定实现：`pipeline._tier_gates`（pipeline.py:267），每级先算各条**判据布尔值**
（result.json `tier_criteria`），再逐级累加得 `tiers`（C 含 D、B 含 C、A 含 B），
report.txt「分层达标」四行与 result.json 同源同值。工单四档 ↔ 判据 ↔ 本次实测：

| 档 | 工单验收行 | 判据（可数） | 本次实测 | 判定 |
|---|---|---|---|---|
| 及格 D | 4表设计合理 | `four_tables`：inspector 存在表数 ≥4 且缺表清单为空 | 4/4 张，缺:无 | 达标 |
| | ORM入库成功 | `orm_insert_ok`：入库行数 >0 且 == 种子数+缓冲数 | 1436 == 500+936 | 达标 |
| | 2条统计查询可用 | `stat_queries`：返回行 >0 的查询数 ≥ min_stat_queries | 3/3 条（T4a 3、T4b 3、T4c 12 行），门槛 2 | 达标 |
| 良好 C | 数据字典完整 | `dictionary_complete`：已登记含义列数 == 总列数且未登记清单为空 | 18/18 列，未登记:无 | 达标 |
| | 批量事务 | `bulk_transactions`：走 bulk_save_objects 且种子、缓冲各自提交次数 ≥2（分批，不是一次性提交） | 种子 5 次＋缓冲 10 次＝15 次，每批≤100 | 达标 |
| | 溯源查询正确 | `traceability`：四表 JOIN 命中告警数 == 告警总数 且 三处外键孤儿行 == 0 | 57/57 命中（100.0%），孤儿 0 | 达标 |
| 优秀 B | 索引优化有EXPLAIN证据 | `explain_evidence`：建索引前计划含 SCAN、建索引后计划含 SEARCH … INDEX、且区间命中 >0 行 | 20000 行基准命中 240 行；SCAN bench_records → SEARCH … USING COVERING INDEX idx_bench_dev_ts | 达标 |
| | N+1问题已规避 | `n_plus_one_avoided`：事件监听计数下预加载 SELECT 条数 < 懒加载条数（loader=joinedload/selectinload） | 懒加载 4 条 vs joinedload 1 条（3 台设备） | 达标 |
| 超优 A | 复杂查询(多表JOIN聚合) | `complex_join_aggregate`：四表 JOIN 聚合桶数 >0 且与逐行手算逐行一致 | 36 桶（3 设备×12 小时），手算互证一致 | 达标 |
| | 导入P3仪表盘闭环 | `p3_handoff`：交接 CSV 已落盘、行数 >0、P3 契约列齐、时间 0 行解析失败、0 未知设备、窗口 ORM=裸SQL | output/p3_dashboard_handoff.csv 36 行×6 列，解析失败 0、未知设备 0 | 达标 |

**证伪口径**（只改 config/rules.yaml、不改代码即可判为未达标，防止橡皮图章）：
| 改哪个键 | 改成 | 塌掉的档 | 实测变化 |
|---|---|---|---|
| n_records / buffer_stand_in_rows | 0 / 0 | D（并连带 C/B/A） | 入库 0 行、可用查询 0 条 |

| index_bench_rows | 0 | B | 基准表空、命中 0 行，EXPLAIN 证据不成立 |
| p3_handoff | 空（关闭交接） | A | 无交接文件、0 行 |

**学生要拿满四档需要自己补的东西**（缺哪项，对应行就打印实测数字并判未达标）：
- D 未达标：检查 `db_url` 指向可写路径；`init_db` 后 inspector 必须看到四表；
  T4a/T4b/T4c 三个查询函数必须真实返回行（返回 0 行多半是测点 metric 或时间桶写法错）。
- C 未达标：① 给 `FIELD_MEANINGS`（core.py:33）补齐 inspector 列出的每一列，报告未登记清单必须为空；
  ② 批量入库必须 `bulk_save_objects` + **每批一次 commit**（循环单条 add 或全程一次提交都不算）；
  ③ 溯源必须让每条告警都能沿 alarms→devices→points→records JOIN 到同刻读数，
  且 records.point_id / points.device_id / alarms.device_id 三处孤儿行均为 0——
  记录指派测点时用 `(设备编码, 指标)` 映射，不要按列表顺序 `zip` 猜（DEF-3 教训）。
- B 未达标：① `index_bench` 要在**独立副本表**上做大样本，先取 EXPLAIN 前计划、
  再用 `engine.begin()` 提交 `CREATE INDEX`、再取后计划，判定看 SCAN→SEARCH USING INDEX
  这类确定性事实而不是"看起来快了"；② 用 `event.listens_for(engine, "before_cursor_execute")`
  数出懒加载与 joinedload/selectinload 各自的 SELECT 条数，并把预加载策略配成非 lazy。
- A 未达标：① 写四表 JOIN 聚合（`count(distinct)` + `avg(case(...))` + `max(level)`，
  告警按 (设备,小时) 外连接）并配一个逐行手算互证函数；② 按 P3 `data_source.CANON`
  的列名与时间格式导出交接 CSV，再用 P3 的读法回读校验（列齐/时间可解析/设备在册）；
  P3 侧缺的生产列由 P3 标"合成·seed"，**P5 不得伪造**。
