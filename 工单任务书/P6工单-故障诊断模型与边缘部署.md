### 知识四要素详解（V1.2深度版·与授课PPT同源）

**B01 建模五步流**
- 定义：五步流=产线SOP：划分→训练→交叉验证→调参→joblib保存
- 使用场景：scikit-learn标准作业程序——顺序即纪律
- 应用实例：joblib.dump(model, 'model_v20260926.joblib')
- 扩展与误区：误区：模型文件叫model.pkl——带版本/日期命名，回滚审计全靠它
- 原理：建模五步流=定任务(分类/回归)→划分(train/test)→训练fit→评估(测试集)→落盘joblib——顺序错则全错（先看测试集再调参=作弊）
- 判断依据：任何监督学习任务按五步走：任务不清不建模、测试集只在最后碰一次
- 逐行解释：X_train,X_test,y_train,y_test=train_test_split(X,y,test_size=0.2,stratify=y) 分层划分；clf.fit(X_train,y_train) 训练；joblib.dump(clf,'m.joblib') 落盘
- 进阶优化：分层抽样保类别比例（不平衡数据必加）；随机种子random_state=42可复现；五步各产出物写进实验记录

**B02 混淆矩阵业务化**
- 定义：混淆矩阵=体检报告四格：对角线判对；FN漏检与FP误报代价不对称
- 使用场景：故障诊断评估不能只看准确率——错在哪类才关键
- 应用实例：FN=漏报真故障(代价高) → 阈值向召回偏移
- 扩展与误区：误区：把混淆矩阵翻译成钱——漏检损失vs误报停机损失，算给业务听
- 原理：混淆矩阵业务化：四格翻译成钱——误报(虚惊)白跑一趟200元、漏报(漏检)停线2万——矩阵每格贴上业务代价，选型才有依据
- 判断依据：汇报不能只报准确率：把混淆矩阵换算成'每月损失/收益'——管理层听得懂的语言
- 逐行解释：cm=[[46,4],[3,47]]; 误报4×200+漏报3×20000=60800元代价 —— 同准确率不同代价，决策树若漏报更少则业务更优
- 进阶优化：代价敏感学习class_weight调权重让模型'怕漏报'；阈值前移（降判故障阈值）以误报换漏报——工程旋钮

**B03 F1与交叉验证**
- 定义：F1=精确与召回的调和平均（谁短谁说了算）；CV=5防一次划分运气好
- 使用场景：类别不平衡(故障样本少)时的诚实指标
- 应用实例：cross_val_score(model, X, y, cv=5).mean()
- 扩展与误区：误区：单次划分90%就报喜——五折均值才有说服力，方差也要报
- 原理：F1=精确率与召回率的调和平均（短板拉分），交叉验证=k折轮流当测试集——单一划分的运气成分被平均掉，结论更稳
- 判断依据：样本量小（几百条）时单次80%可能是运气——5折交叉验证均值±波动才是可信成绩
- 逐行解释：from sklearn.model_selection import cross_val_score; cross_val_score(clf,X,y,cv=5,scoring='f1').mean() 五次考试平均分——std大说明模型不稳
- 进阶优化：StratifiedKFold不平衡数据保比例；留一法LOO小样本极限版；网格搜索里的cv参数同一机制

**B04 推理服务化**
- 定义：服务化=模型坐上窗口：POST JSON特征进→predict→JSON结论出
- 使用场景：模型从notebook走向服务——部署第一步
- 应用实例：http.server处理POST /predict，标准库即可
- 扩展与误区：误区：接口没schema约定——请求字段错一个静默出错结论，契约先行
- 原理：推理服务化=模型包成HTTP接口：POST特征JSON→响应预测结果——模型从notebook变量变成生产线上的服务
- 判断依据：边缘网关/中台调用模型的统一形态：granian/asgi起服务，input schema校验——模型即API
- 逐行解释：@app.post('/predict') async def predict(x:Input): return {'cls':int(clf.predict(x.vec)[0])} —— 输入pydantic校验+输出JSON，工程接口两件套
- 进阶优化：模型版本化（v1/v2路由共存灰度）；A/B分流对比线上效果——服务化的进阶形态

**B05 warmup与p95**
- 定义：warmup=发动机热车：首次调用加载模型慢，预热后再测；p95=95%请求的耗时线
- 使用场景：延迟验收口径：p95不是平均值——体感由慢请求决定
- 应用实例：先curl一次预热，再压100次取95分位
- 扩展与误区：误区：只报平均延迟——1次10秒卡住用户体感，均值全被掩盖
- 原理：warmup冷启动预热+p95延迟：首次推理要加载模型（秒级慢），先空跑几发预热；p95=95%请求都快于此值（长尾才是体验）
- 判断依据：服务上线验收看p95不看均值——均值被快请求拉低，用户疼的是那最慢的5%
- 逐行解释：启动时for _ in range(5): predict(dummy) 预热填缓存；p95=np.percentile(lats,95) 从延迟分布取——压测报告两件套：warmup耗时+p95
- 进阶优化：p99更严苛（金融级）；延迟直方图定位长尾来源（GC/磁盘/队列）；超时熔断防雪崩——SRE三件

**B06 服务健康自检**
- 定义：/health=服务的心电监护：GET返回模型版本与状态
- 使用场景：部署后'活着吗'的标准问法——运维可见
- 应用实例：{'status':'ok','model':'v20260926'}
- 扩展与误区：误区：health与metrics混一谈——health管活没活，metrics管好不好
- 原理：服务健康自检=/healthz端点：进程活着(code 200)≠模型可用——自检要真推理一发验证依赖全通（模型文件/内存/下游）
- 判断依据：K8s/守护进程靠健康检查决定重启——假活（进程在模型坏）最坑，自检必须测到'真推理'
- 逐行解释：@app.get('/healthz'): try: predict(sample); return {'ok':True} except: raise 503 —— 真推理一发，模型/依赖/内存全链路过一遍
- 进阶优化：就绪/存活双探针（readiness+liveness分开语义）；自检也打心跳日志——故障时间线可回溯
